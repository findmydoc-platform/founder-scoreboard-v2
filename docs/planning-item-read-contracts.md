## Shared guarantees

### Scope, selection and coverage

Completeness follows the task's authorized scope. Collection membership, contextual records and Item existence are separate. A partial collection can be useful; exact totals, direct-child progress, blocker signals and dependent actions need their own complete bases. Missing, not loaded, loading, partial, stale, unverified, unavailable and forbidden are distinct from proven empty. Never turn unknown into zero, finished or unblocked.

The shared module owns status normalization, literal search, ownership fallbacks, relationship direction and ordering. Database scope, matching, eligibility, hierarchy, personal Sub-Issue parent inclusion, semantic ordering and deterministic ties precede page limits. Exact set summaries include relevant off-page records. The server hydrates only requested content and required context. Local selection requires a demonstrably complete suitable basis and an applicable contract.

Search preserves the existing fields in `planning-task-table-view-model.ts` and `taskText`: title, description, assignee, workstream, priority, Definition of Done, fixed date, repository, canonical and legacy Issue URLs/numbers, normalized status, parent Initiative title/goal, Sprint name and Review owner name. Trim input and preserve German case normalization and literal substring matching. `%`, `_`, backslash and brackets are literal characters, not SQL pattern instructions. Quick filters combine with OR; additional filters combine with AND. Personal inclusion uses qualifying open assigned Sub-Issues, while extra filters still evaluate the parent Deliverable. Sub-Issues do not become standalone Board cards.

Ownership uses assignee identity, then assignee value, then owner identity, then owner value. A present foreign assignee does not fall through to a matching owner. Relationship direction follows existing `effectiveTaskRelation` semantics in both directions. Direct-child progress does not count grandchildren.

Preserve the compatibility starting point of up to 20 initially visible completed cards. This is not a universal page size, retention period, completion timestamp policy or new 30-card/30-day rule. Provider caps are implementation limits. Complete contracts enumerate their required basis or fail explicitly through their established format.

### Authority, consistency and client acceptance

Every access, aggregate, revision check and continuation retains its own authorization through the existing credential module. Identity resolves through `profiles.auth_user_id = auth.uid()`. Database checks are at least as strict as the app action. Reuse retains original user/session bindings and deadlines, original JWT checks and applicable operation permits. An unchanged source revision grants no authority.

Selection, summaries, supporting reads and hydration need one snapshot or equivalent revision evidence spanning the whole read. Joint assertions require compatible complete foundations; independent tasks need no global snapshot. Contributing sources include lifecycle, hierarchy, strategy, RACI, relationships, blockers, links, profiles, project/Sprint data and each consumer's additional records. A source counter may invalidate conservatively. Item timestamps, same-count results or a whole-model digest alone cannot certify every source. Comment-only changes are a required counterexample.

Time-dependent results use a controlled evaluation time and an identifiable validity boundary. Current-Sprint, deputy and objection/review windows can expire without a write. Source equality does not renew time or authority.

Invalidate potentially affected membership, ordering, totals, signals, summaries and continuations after confirmed or observed relevant changes. If the affected subset is unknown, invalidate its whole potentially affected contract. Invalidation marks evidence stale; it does not force a reload. A partial client collection cannot invent exact replacement totals.

Keep Item fields and query coverage separate. Omitted fields do not clear details. A newer Item version leaves unreconfirmed older fields stale. Multiple partial results do not establish completeness. Continuations bind authorized scope, normalized query, ordering, revision and temporal basis. Reject incompatible continuations and restart only the affected scope. Never merge incompatible page generations as complete.

The existing Planning-state owner accepts results. Fully reject obsolete success, including fields and coverage, when user, session generation, original authority deadline, scope, query generation, invalidation or applicable page base no longer match. A later request start is not proof of newer state. Current-scope denials remain effective after a query change; old-session denials cannot block a replacement session.

First successfully stored writes against one base win. Stale writes conflict explicitly. Preserve drafts and unconfirmed timeout outcomes. Matching fields do not confirm an operation. Page absence establishes neither deletion nor denied access. Authoritative lifecycle results govern removal/restoration; late reads cannot resurrect removed content. Logout, known revocation and account/session replacement immediately clear affected protected content.

### Scheduling and reveal

| Trigger | Required behavior |
| --- | --- |
| Current task or explicit interaction | Prioritize required reads, including detail, expanded children, a further page and an action basis. |
| Visible independent secondary area | Request independently, at lower priority. Reveal as soon as useful. Optional header, Calendar or Quick Links never gate main content. |
| Hidden view | Load when used; no default hidden-view prefetch or independent polling. |
| Text search | Start 250 ms after the last input; Enter starts immediately. |
| Related filters in one interaction | Produce one normalized query rather than intermediate requests. |
| Automatic affected-content refresh | Collect needs of the active view; start after 500 ms without another relevant change. |
| Explicit refresh or current action basis | Bypass the quiet window. |
| Active visible external-change observation | Lightweight revision check every 60 seconds and on return, visibility restoration and restored connectivity. |
| Missing or known-stale content | Request required content directly; no redundant preliminary revision request. |
| Current sufficient authorized content | Reuse without an equivalent content request. Fresh accepted hydration causes zero immediate equivalent complete reads solely due to mount/return. |
| Unchanged valid revision | No content read. Version-only observation does not enumerate/hydrate Items, compute exact aggregates or hash the model. |
| Failed revision observation | Freshness unverified; no renewed authority and no complete-read fallback. |
| Further changes during an in-flight read | Accumulate necessary remaining demand. Do not start one request per write. |
| Continuous changes | Affected content may remain explicitly stale until quiet or explicit use. Independent work continues. |
| Known-invalid further-page basis | Do not send it. Restart the affected collection directly. |

Coalesce only equivalent work with compatible user/session, authorized scope, normalized query, required coverage and revision. Repeated page clicks share demand. Suppress superseded queued queries. Keep a shared read alive for remaining consumers; when none need it, propagate cancellation through supported browser/server/data access. Cancellation, actual backend termination and response rejection are different observations. Never cancel writes or durable sync due to UI demand.

Same-query refresh/pages preserve focus, scroll anchor, selection and inputs. A deliberate new query starts at its first result and keeps control focus. Pending replacement results remain attributed to the prior query. Return restores saved position where possible. Open detail follows Item identity and retains its draft after membership changes. Defer disruptive presentation changes during an active interaction with a stale indication. If focus disappears, move it to a remaining control or area heading. Authorization loss takes effect immediately.

Use subtle, accessibly named feedback for loading, stale, unverified and failed states. Targeted retry repeats only missing demand. Failed secondary reads retain independently useful authorized content. Automatic failures do not create retry loops; regular checking, renewed use, restored connectivity or explicit retry resumes work. Required stale/incomplete action foundations continue to block only their dependent actions.

## Shared-loader and retirement accounting

`loadPlanningItemsForReadModel` currently serves **Team, Profile, Notifications and Sprint**. Sprint indirectly supplies tasks, assignment, Review, assessment and completion. Profile supplies Initiative options. Notifications supplies Item references. Replacing one caller does not retire this loader for the others.

`loadPlanningWorkspaceModel` currently serves **Planning Board/complete views and the strategic adapter**. Planning complete views indirectly supply table, structure, Gantt and selectors. The independent **Backlog**, **detail/children**, **release**, **external context**, **digest** and **GitHub** readers also require accounting. Header counts and optional header slots have their own read paths. Trash detail/lifecycle and GitHub webhook/durable jobs retain their existing security and mutation contracts; reads contributing to reconciliation remain under GITHUB.

## Evidence, enforcement and exceptions

The specification requires `verify:planning-reads` to run both the resolved production dependency verifier and executable allowed/rejected fixtures, with explicit CI execution. It also requires explicit `verify:credentials`, Unit, Storybook and real isolated integration execution. These are required future enforcement artifacts, not commands claimed to exist at this inventory stage. Builds alone do not prove architecture fixtures ran.

For each consumer, record evidence owner, source commit, fixture identity/size, actor/auth mode, evaluation time, useful endpoint, deterministic results, applicable cold/warm samples and gate judgment. Keep one-off measurements, raw traces, screenshots, plans and run reports outside the repository. Publish only safe reproducible summaries, without service credentials, raw identities, Item contents or private endpoints. Synthetic fixture identities and text are safe test data.

An exception record must name consumer ID or exact dependency edge, violated rule, concrete reason, responsible maintainer, substitute evidence and expiry condition or fixed review date. A verifier exception allows only that edge and includes an accepted example plus a rejected neighboring bypass. There are no blanket directory exemptions or general disable switches. An exception cannot weaken authorization, call partial complete or silently revise another approved guarantee.

Every stage gate remains in specification #641. Stage 0 requires complete accounting, independent expectations and a current isolated stage-1 baseline. Stage 1 requires no immediate redundant complete read after accepted hydration and repeatably shorter entry/return. Stage 2 requires real SQL parity/traversal/totals/off-page evidence and bounded card output as history grows. Stage 3 requires identity/candidate/child/Backlog/Gantt evidence. Stage 4 requires independent areas and complete metrics/counts/release matches. Stage 5 requires complete authorized decisions. Stage 6 requires machine compatibility and final reader retirement. A failed gate stops advancement. Revert only to an already verified compatible authorized path; otherwise retain an explicit stale/unavailable basis.

# Planning Item read verification

This is a recurring procedure for verifying [read contracts](planning-item-read-contracts.md) before migrating a consumer. Specification #641 owns the gates. Keep each run's plans, drivers, raw observations, screenshots and results outside the repository. The repository retains reusable contracts, fixtures and behavioral checks only.

## Disposable runtime

1. Record unchanged source commit, lockfile digest and pinned CLI/browser/runtime versions. Quarantine registered environment files without displaying values. Build an explicit environment allowlist containing only disposable values. A registered project environment or copied worktree does not authorize its services for experiments.
2. Provision a unique Supabase project outside the repository, free ports and new project-specific volumes/network. Copy committed migrations. Disable external providers, mail forwarding and automatic seed until the guarded step. Verify the project identity and owned volumes before reset or mutation. Keep a deny-by-default outbound policy for the app and drivers, permitting only the owned local services. Never print CLI status containing generated credentials.
3. Apply the committed schema and materialize the complete synthetic variant. Use real local Auth and authoritative profile binding for browser work. Record counts and expected identities separately from the query under test. Keep provider adapters deliberately controlled for integration cases and identify those controls in the evidence.
4. Start unchanged app code with its own build output. Local-login mode currently requires development mode; report a development baseline as development evidence. Warm module compilation separately. Do not imply production-build timing or real Workspace-provider latency.
5. Run only one fixture/runtime owner at a time. Never reset while another sample or test uses the stack. Teardown in `finally`, including after failed setup or measurement. Stop and remove only owned resources. Verify pre-existing local projects were untouched. Remove private runtime credentials after safe evidence extraction.

A fixture or service failure leaves the gate unmet. A skipped/no-tests integration project is not execution evidence. Source inspection, mocked HTTP, a historic measurement and a rendered shell do not establish the current stage-1 journey.

## Stage-1 journey and endpoint

Use real browser interaction with unchanged app, real disposable Auth, actual API/database reads and the existing client owner. At a recorded viewport, enter Planning with the literal query `100%`. The independent expected Deliverable is `fixture-literal`; the wildcard decoy does not match. The useful endpoint is a truthfully attributed card whose real detail-opening action is available and successfully opens that identity. Record card readiness and the subsequent detail-readiness interval separately. A page title, request completion or DOM marker alone is insufficient.

Leave through actual workspace navigation and return with the same session/query. Verify the expected card remains operable, the query/selection is truthful and relevant interaction state is retained. Record immediate equivalent complete-model requests caused by mount/return, including their absence when established. Do not impose stage-1 future behavior on the unchanged baseline: record current requests honestly, then compare after the coordinated change.

Exercise the independently specified old completed search and proven-empty query. Record each result's coverage and counts. Use controlled adapter/unit cases for deliberately reordered success, failed optional reads, known stale data and session replacement. They complement the live baseline rather than substitute for it.

## Matched comparison conditions

Before each run, fix data variant, role, authentication mode, authorized scope, evaluation-time treatment, query and viewport. Keep these dimensions separate:

| Profile | Browser HTTP cache | Page/modules and client owner | App process | Provider/database | Authorization evidence |
| --- | --- | --- | --- | --- | --- |
| Browser cold / entry | New context, cleared cache | No prior page/client state | Explicitly state reused or restarted; compile before timed samples if reused | Explicitly state warm/reset and controlled provider behavior | Genuine login established outside timed interval; record whether evidence may be reused |
| Warm / return | Same controlled context | Navigate away/return with reused page/module/client state as actually observed | Same warmed process | Same unchanged fixture and provider state | Same valid session, original deadlines retained |

A cold browser does not imply a cold server, provider or database. Collect at least five independent samples per compared cold/warm profile. Use equivalent resets and authentication preparation for before/after. Report individual safe durations, median and range, variability and adverse results. Do not infer production percentiles, a universal millisecond target, speedup percentage or page-size policy.

Measure first usefulness, supplementary reads, next interaction, additional pages and refresh separately. Work started after the useful endpoint does not extend that endpoint. Observe authorization, database work, hydration, serialization/transfer, server CPU and browser work only where instrumentation actually covers them. Identify unavailable observations rather than deriving them from payload size or overlapping timings.

Keep started requests/backend attempts, suppressed requests, coalesced work, propagated cancellation, observed backend termination and accepted/rejected responses distinct. Check instrumentation buffers for truncation and state collection overhead. Existing runtime logging may help but is not a complete critical-path trace by itself.

## Safe run record and acceptance

Each external run record includes source/fixture digest, exact variant sizes, actor role/auth mode, controlled time, viewport, all cache/process/provider/authority conditions, useful endpoint, per-sample results, deterministic expected-versus-actual identities/counts, request observations, instrumentation limits, failures and teardown result. Link the safe summary from the owning ticket/PR when publication is requested. Do not commit private runtime paths, raw traces, tokens, service endpoints or machine-specific addresses.

A current pre-change baseline plus reproducible expected results satisfies only the comparison-basis requirement. Each later consumer needs its own baseline before migration, own executable contract evidence and applicable controlled benefit comparison. A failed gate stops advancement. Any adverse trade-off, proposed representative or exception needs the explicit evidence-backed judgment required by the specification.

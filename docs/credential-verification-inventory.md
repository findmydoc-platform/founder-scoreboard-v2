# Credential verification inventory

This inventory records the implemented credential boundaries for spec #487, including contract closeout #502. It applies Parnas's Information-Hiding Criterion and Robert C. Martin's Dependency Rule. Tests follow Freeman and Pryce's Outside-In TDD and Kent Beck's Test Desiderata. It records actual callers and credentials, including supported public and development contracts. It does not claim production deployment or the separate #503 measurements. The production acceptance documented in `docs/logging.md` predates the calendar snapshot implementation and remains historical evidence for that deployed commit.

## Ownership and migration

The public server entry is `authorizeCredentialAction` from `@/lib/credentials`. Its input contains a credential and a semantic action. No caller chooses an adapter, cache lifetime or verification mode. `credentials/types.ts` exports types without runtime secrets. `credentials/internal/` is private. Server adapters are marked server-only; the isolated browser transport is marked `"use client"` and cannot import server adapters or an Auth SDK. The shared session policy now lives in `credentials/internal/session-policy.ts`. The former `authz.ts` guards, legacy delegation and client-argument compatibility adapters are removed. Production callers use concrete application actions; verification-only public guard variants are removed. No legacy dependency or transport allowance remains.

The action result preserves the existing discriminated `ok` result, safe HTTP status, German message, optional error code and session authority. It exposes no Supabase client, provider token or service credential. Session requests support explicit Bearer and server-owned cookie transport. Personal and technical credentials have separate action adapters. The original expand step added no cache or evidence claims. #489 adds `calendar.read` to this same entry. It returns a fixed calendar read capability with ordinary promises and data results, never an SDK query builder, Auth client or token. Subsequent families extend this same public entry.

The calendar implementation verifies the exact JWT through the installed Supabase SDK. ES256 uses cached JWKS and local cryptographic verification; a supported symmetric JWT uses the SDK's authoritative Auth fallback. The configured signing-key type was inspected read-only and required no rotation. A process-local, bounded membership cache and equal-key single-flight retain the original verification start and expire at the earlier of 900 seconds or JWT expiry. Keys include exact credential fingerprint, user, session, profile, Google subject/email, issuer/audience/scopes, intended action and policy/provider configuration. Distinct instances share no membership cache.

Role reads remain live, which is stricter than the permitted 15-minute allowance. Mutable Auth-user validity and exact Workspace/profile/Google binding also remain live before each user data operation. Session policy stays authoritative at authorization and individual permit issuance. Cached membership does not replace these checks, profile authorization, configuration checks or any data query. Each operation obtains its own method/path/JWT-bound permit and releases it without replay. The private calendar capability exposes only `readSnapshot(earliestDate)`. Its internal adapter reads published-owner IDs and date-filtered publications through a profile-root relationship query, then follows per-owner publication cursors to the oldest relevant tail marker when the embedded page is truncated. Profile pages use an exact count and ascending ID cursor; publication pages use the descending date, revision and ID cursor. It validates completeness and returns no partial snapshot on errors or inconsistent page progress. Every additional HTTP request uses the same bound client and independently rechecks authority, obtains its permit and releases it. The multi-request snapshot is not a database transaction. The route still owns range validation and response projection. An expired context cannot issue another query. Proxy has its own cookie-session verification; it shares no process-local evidence with route instances.

The private draft GET and POST use `workweek.private.read` and `workweek.private.write`. Both reuse the internal verified session context; their public results contain separate fixed read or save capabilities. No caller receives an SDK, token or service client. The read capability owns the preparing automatic publication, published owner publications, pending publication, latest non-retired owner draft and selected edit-context operations. Source-publication, conflict-resolution publication and expired automatic-source reads remain conditional. All user reads retain separate permits and explicit owner filters. The resolving-conflict service lookup has a separate live user authorization and owner/version/state restrictions. The selected edit context is requested once, and mixed publication snapshots still return `edit_context_stale` with HTTP 409. Save capabilities invoke only the existing owner-bound draft RPCs; publication, restart and provider mutation protocols are unchanged.

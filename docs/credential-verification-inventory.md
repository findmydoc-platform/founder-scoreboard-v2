# Credential verification inventory

This inventory describes the integration base for spec #487. It applies Parnas's Information-Hiding Criterion and Robert C. Martin's Dependency Rule. Tests follow Freeman and Pryce's Outside-In TDD and Kent Beck's Test Desiderata. It records actual callers and credentials, including supported public and development contracts. It does not claim that migration or deployment is complete. The calendar route currently makes one full publication read and a separate published-owner read, and derives the selected range locally; historical counts in the spec describe an older analysis revision.

## Ownership and migration

The only new public server entry is `authorizeCredentialAction` from `@/lib/credentials`. Its input contains a credential and a semantic action. No caller chooses an adapter, cache lifetime or verification mode. `credentials/types.ts` exports types without runtime secrets. `credentials/internal/` is private and marked server-only. The shared session policy now lives in `credentials/internal/session-policy.ts`. Existing `authz.ts` guards delegate to the public seam, and `legacy-session.ts` returns only safe metadata from that policy. Two existing client-argument compatibility adapters remain internal until their sibling consumers migrate. Their one exact dependency allowance is temporary debt, removed in #502.

The action result preserves the existing discriminated `ok` result, safe HTTP status, German message, optional error code and session authority. It exposes no Supabase client, provider token or service credential. The first adapter accepts Bearer request transport through existing guards. #491 adds cookie and browser lifecycle transport; personal and technical credential variants enter through later vertical slices. They must not become caller-selected verification strategies. The expand step added no cache or evidence claims. #489 adds `calendar.read` to this same entry. It returns a fixed calendar read capability with ordinary promises and data results, never an SDK query builder, Auth client or token. Subsequent families extend this same public entry.

The calendar implementation verifies the exact JWT through the installed Supabase SDK. ES256 uses cached JWKS and local cryptographic verification; a supported symmetric JWT uses the SDK's authoritative Auth fallback. The configured signing-key type was inspected read-only and required no rotation. A process-local, bounded membership cache and equal-key single-flight retain the original verification start and expire at the earlier of 900 seconds or JWT expiry. Keys include exact credential fingerprint, user, session, profile, Google subject/email, issuer/audience/scopes, intended action and policy/provider configuration. Distinct instances share no membership cache.

Role reads remain live, which is stricter than the permitted 15-minute allowance. Mutable Auth-user validity and exact Workspace/profile/Google binding also remain live before each user data operation. Session policy stays authoritative at authorization and individual permit issuance. Cached membership does not replace these checks, profile authorization, configuration checks or any data query. Each operation obtains its own method/path/JWT-bound permit and releases it without replay. The same private verified context supplies both calendar queries. An expired context cannot issue another query. Proxy has its own cookie-session verification; it shares no process-local evidence with route instances.

The private draft GET and POST use `workweek.private.read` and `workweek.private.write`. Both reuse the internal verified session context; their public results contain separate fixed read or save capabilities. No caller receives an SDK, token or service client. The read capability owns the preparing automatic publication, published owner publications, pending publication, latest non-retired owner draft and selected edit-context operations. Source-publication, conflict-resolution publication and expired automatic-source reads remain conditional. All user reads retain separate permits and explicit owner filters. The resolving-conflict service lookup has a separate live user authorization and owner/version/state restrictions. The selected edit context is requested once, and mixed publication snapshots still return `edit_context_stale` with HTTP 409. Save capabilities invoke only the existing owner-bound draft RPCs; publication, restart and provider mutation protocols are unchanged.

## Shared role and administrator migration

Issue #493 uses the same verified session/data context as the workweek adapters for all shared guard actions. The existing CEO/founder/deputy/viewer sets and `sessionAuthority` capability policy remain authoritative. Role reads stay live. A received active administrator snapshot cannot exceed its actual expiry. Required snapshot failure still denies administration; optional snapshot failure does not remove an otherwise granted planning role. Only permitted local host/environment combinations retain simulation, and simulation cannot activate administrator access.

Administrator inspection, activation, ending, eligibility changes, technical identity updates and directory reads use fixed public actions. Mutation capabilities bind their target profile when issued and invoke only the existing user-bound RPCs. The directory capability supplies fixed reads for the directory, notification events, deliveries and the configured project. The feature retains mapping, filtering and provider-status orchestration. HTTP and SSR use the same policy. Neither path receives a client, token or generic query interface. Per-operation database authorization remains effective after activation ends or expires.

One exact temporary edge from `authz.ts` to `credentials/internal/legacy-session-client.ts` preserves these existing client-argument consumers until their owning sibling migration:

| Existing compatibility API | Remaining production consumers |
| --- | --- |
| `requireTeamMemberForSession(client)` | `src/app/api/tools/preview-image/route.ts` |
| `resolveAdministratorAccessFailure(client)` | `src/features/planning-items/model/planning-item-revision.ts`, `src/app/api/tasks/[id]/relationships/route.ts`, `src/app/api/founderops-settings/github-project/route.ts`, `src/app/api/notifications/deliver/route.ts` |

The existing server-only `bearerToken(request)` compatibility getter now selects the real request transport through the internal resolver. An explicit Authorization header takes precedence over cookies, and protected cookie mutations retain origin checks. The getter remains only for existing sibling resource migrations. No new credential kind or client-argument public action is introduced. #504/#505/#510 migrate their consumers; #502 removes the compatibility exports and exact allowance.

## GitHub installation migration

Issue #495 moves App JWT signing, installation access acquisition, expiry handling, process-local reuse and installation operational status into the private credential adapter. The existing runtime private-key file import is confined to that adapter. The public entry returns a constrained installation transport for a semantic action and explicit repository target, never a token. Configuration fingerprints bind app identity, installation ID and key configuration; repository bindings distinguish cache entries. Reuse ends five minutes before the provider expiry. Concurrent misses share one acquisition, including the same sanitized failure. Cache entries are bounded and resource mutations are never replayed after a credential or network failure.

All nine production acquisition families now use the public entry:

| Actual caller | Action and continuing resource ownership |
| --- | --- |
| Task sync route | `github.projection.apply`; `projectTaskToGitHub` retains preflight, lock, locked reload, CAS, hard and warning projections, persistence and typed cleanup |
| Planning Items GitHub execution | `github.projection.apply`; preflighted task projections remain serial |
| Planning trash lifecycle | `github.lifecycle.apply`; existing durable claims, desired-state issue updates and comment markers remain in the workflow |
| Planning webhook processing | `github.issue.read`; current issue, relationship and Project observations remain resource adapters |
| Issue-comment webhook processing | `github.issue.read`; explicit delivered repository and received issue identity remain authoritative |
| Task GitHub comments route | `github.issue.read`; explicit task repository, evidence permission and comment import rules remain authoritative |
| GitHub Project administration route | Separate `github.project.read` and `github.team.read`; administrator activation and transaction authority remain independent |

| GitHub asset relay | `github.asset.read`; exact initial URL, host allowlist, manual redirects, redirect limit and image response check remain effective |

The GitHub status route and administration read model obtain safe operational status through the same entry. Status makes a bounded read and compares the returned installation ID with configuration. Its output contains no provider diagnostics or key paths. A usable installation never grants a FounderOps role or a personal-token action. The user-token vault, OAuth connection and user-authored comment, review and attachment credentials remain separate for #496.

`github-http.ts` remains the only API transport. Resource functions accept the opaque installation capability while retaining legacy user credentials until #496. The capability checks HTTPS API origin, allowed repository/search targets, semantic read/write limits and exact existing GraphQL documents before dispatch. Static documents are shared with their resource adapters; domain interpretation and orchestration stay outside credentials. Repository variables are checked against the target; GitHub remains authoritative for granted provider permissions, opaque node IDs and Project visibility. Installation issuance requests only the target repository names. It preserves configured provider grants rather than requiring new grants.

Asset downloads stay outside GitHub JSON API semantics. Their private adapter checks every redirect and sends installation Authorization only to `github.com`, never to a CDN. The route receives a response, never a credential. The dependency policy removes migrated legacy edges and the route's network allowance. No broad library or filesystem exception is added.

Observable coverage uses the public entry and real comments, native relationship and archive resource workflows with synthetic GitHub responses. It covers warm and expiring access, concurrent acquisition, changed installation, denied target, provider denial/unavailability, read-only access, exact GraphQL restrictions, private diagnostics and ambiguous mutation success followed by resource reconciliation. Existing projection, serial execution and HTTP metadata suites retain their contracts. No production provider or database is needed for this slice. These tests measure controlled protocol behavior and make no claim about production request duration.

## GitHub authored connection migration

Issue #496 moves the GitHub OAuth state, code exchange, configured-account lookup, encryption, vault access, refresh, status and disconnect into private credential adapters. Connect and callback routes use the public entry with the existing server-owned cookie session. A signed state retains its ten-minute deadline, exact Auth user and profile binding and safe relative next destination. The callback verifies the provider account against the current configured login and persists the stable GitHub user ID. The existing unique active-account constraint, AES-256-GCM ciphertext and separate access/refresh expiry remain authoritative. A delayed callback cannot replace a newer connection.

Authored comment and review capabilities identify their durable delivery and claim, rather than accepting a profile chosen by a caller. The module loads the actual source author, active task, repository and issue and verifies the live claim before every resource call. It permits only that issue's comment reads and a marker-bound comment write. Preview access separately verifies the existing operational-lead or dedicated delivery-secret authority. Attachment access verifies the requesting session and the existing task-detail permissions and permits only its exact Contents target. Credentials, SDK clients and decrypted strings never leave these adapters. Installation capabilities still cannot perform user attachment uploads.

The additive migration extends only the existing service-only GitHub vault:

| Added state or operation | Necessity and boundary |
| --- | --- |
| `connection_id` | A fresh UUID for each connection prevents disconnect/reconnect ABA and rejects stale callback or resource capabilities |
| `credential_version` | CAS distinguishes rotation snapshots without treating usage timestamps as credential changes |
| `refresh_claim_id` | One durable owner can attempt the rotating refresh exchange; another instance cannot reuse the same snapshot |
| `refresh_claim_expires_at` | A late provider result cannot commit after its ownership deadline; an expired claim is never reassigned |
| Store RPC | Locks the configured profile and applies the expected connection/version before replacing ciphertext |
| Claim RPC | Atomically binds profile, connection and version and admits a single provider attempt |
| Finalize RPC | Atomically checks configured login, connection, version, claim and deadline before replacing ciphertext or recording a safe failure |
| Use/disconnect RPC | Records use against the current snapshot; disconnect removes only the expected connection, including its legitimately refreshed versions |
| Profile association trigger | An actual configured-login change invalidates only that profile's GitHub connection and any in-flight refresh |

All new RPC execution is denied to PUBLIC, anon and authenticated. Only the server role can call the four vault RPCs. The narrow trigger function grants no direct Data API action. Existing vault RLS and table grants remain unchanged. Profile-first locks serialize absent-row OAuth CAS as well as rotation and identity changes. The migration preserves existing ciphertext, expiries, IDs and timestamps and can be applied again without replacing connection IDs.

A lost refresh response cannot reveal an unknown rotated secret. The durable claim remains blocked and reconnect is required; no instance blindly exchanges the old refresh again. Successful rotation preserves a non-replaced refresh token and its individual expiry when the provider omits them. Last-used recording and live configured-account checks continue on ordinary access. No resource mutation is retried because of a credential response or renewal.

The browser retains a random attachment operation ID in memory and session storage after an unknown HTTP result. A manual retry of the same task, filename, MIME type and bytes reuses that ID; a confirmed success clears it, so a deliberate later upload receives a new ID. The server binds the target to task, current author, operation ID, filename and MIME type. Legacy callers without an ID use a content-derived target. The ID grants no authority: every request repeats the session, task and owner checks. The resource workflow observes the target and compares Git blob identity before writing. After an uncertain PUT it observes again and accepts only matching content. A later retry also observes first; conflicting content is never overwritten. Comment and review orchestration, markers, serial claims/finalization and reconciliation remain in their existing feature workflows.

Tests exercise real connect/callback routes and the public entry with scripted Auth/GitHub responses. Durable tests use an isolated local vault and real PostgREST for cross-instance contention, stale finalization, reconnect, unknown rotation outcomes, mutable association changes, usage, disconnect and every new RPC's denied user/anonymous access. The real comment outbox proves reconciliation after a lost success response. A migration test checks preservation, repeat application and service-only privileges. These are controlled protocol and database checks, not production timing measurements.

## Executable dependency rule

`pnpm verify:credentials` runs compiler-resolved fixture projects and the repository check. `pnpm build` also runs the repository check before Next.js compilation. Resolution honors `@/` and relative imports. The check visits imports, re-exports, namespace imports, literal dynamic imports, import-equals and CommonJS. New helpers cannot indirectly expose an internal adapter or a protected legacy entry because the helper's own edge fails. Non-literal runtime loads fail closed. Type-only imports remain usable.

The Directory adapter now lives inside the module. Its old export is an explicitly allowed compatibility edge for remaining callers, removed by #502. The calendar route no longer has a legacy guard or unrestricted data-client edge.

The checked-in policy lists exact current source/target legacy edges and bounded network identifier references per file. It does not exempt `src/lib` or another directory. New SDK imports, protected helper dependencies and network references require approved internal adapter ownership. This is deterministic architecture enforcement, not a sandbox for malicious JavaScript. Approved internal adapters may use provider SDKs and transports. New public callers may import only the public seam or runtime-free types. Keep allowances shrinking as families migrate; do not regenerate a baseline to hide violations. #502 removes legacy allowances and delegation, and #503 validates the complete application and client bundle.

## Evidence and remaining work

#488 preserves existing authorization behavior and adds executable dependency acceptance/rejection fixtures. Focused seam tests use real guards and Supabase protocol handling with scripted external responses. They verify missing credentials, allowed founder planning access and denied CEO action. No existing database is reset, no provider is contacted and no performance improvement is claimed. #489 adds controlled-clock, real ES256 signature, warm/expired evidence, single-flight/failure, credential/session/scope/user separation, instance replacement, live mutable binding and safe query-failure coverage through the actual calendar route and public seam. Focused disposable PostgREST tests retain JWT rejection, permit method/path/generation/expiry, session removal, user ownership and blocked direct REST/RPC/Storage access. These tests use local synthetic credentials and scripted Auth/Directory responses; they do not claim production timings. Remaining credential rotation, browser consumer migration and whole-application acceptance belong to the subsequent tickets. Comparable full HTTP measurements must retain the earlier baseline's HS256, Proxy, dataset and protocol conditions; ES256 route-only unit counts are a separate observation.

#490 adds real private-draft GET/POST protocol tests for base and conditional reads, selected/future/recovery behavior, safe responses, validation and query failures, denied or expired credentials, capability separation and the original membership deadline. The disposable PostgREST case crosses the actual routes with real JWT/permit/RLS enforcement, two owners, a foreign published baseline and session removal. Equivalent empty edit snapshots may share the existing snapshot hash; this does not select another owner, because the save RPC derives its owner from the current authenticated binding. The context-hash and publication protocols are preserved.

#491 moves cookie acquisition, Proxy, SSR navigation and the login/link/callback/logout entry points behind the same module. Proxy constructs its response after awaited renewal and propagates the resulting cookies to both the downstream request and response. SSR planning/home uses the existing exact-token verification and constrained data context; its original verification start includes preceding cookie-session work. Google login still verifies the actual provider identity, consumes the existing login/link nonce where required, records the session, and checks admission after the recording write. Calendar connection credentials remain separate.

The server browser transport provides a verified identity, opaque credential revision and expiry without returning tokens. Same-origin JSON mutations bind recovery/global logout/local clearing to the expected user and revision. Credential errors and temporary Auth failures retain different outcomes. A replacement login creates a random cookie generation. Refresh and callback responses write only their own generation, never the active-generation pointer. Logout marks that generation revoked, so a delayed refresh cannot restore it. Pointerless legacy sessions use a fixed compatibility generation; even their first renewal cannot overwrite a newer login pointer. Explicit replacement retires cookies from preceding generations. Canonical SDK cookies remain a temporary compatibility mirror until #492 migrates every browser reader and removes that mirror. They do not determine the new server transport's active generation. Browser callers must serialize explicit login starts and reject obsolete navigation/recovery results; #492 owns those consumers and their cross-tab coordination.

Focused Chromium tests use the real Next.js routes, SDK, Proxy and browser cookie jar with a local synthetic Auth protocol. They delay a refresh until after a newer login or global logout, deliver its actual `Set-Cookie` headers, and verify the resulting active identity. They also verify application-session cookies omit the OAuth provider token. These results establish cookie behavior under the scripted protocol, not production provider latency or cross-instance cache sharing.

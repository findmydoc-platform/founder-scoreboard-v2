# Credential verification and action authorization

`authorizeCredentialAction` from `@/lib/credentials` is the public server entry for credential decisions. Callers supply a factual credential, semantic action and applicable target. They do not choose a verifier, adapter, cache duration, refresh strategy or unrestricted transport. Public results contain fixed operations and safe metadata, not SDK clients, query builders, service credentials or provider tokens. Result shapes remain action-specific; HTTP parsing, response mapping and domain workflows stay with their features.

This module applies Parnas's Information-Hiding Criterion and Robert C. Martin's Dependency Rule. [ADR 0002](adr/0002-central-credential-verification.md) records the rationale, alternatives and risks and retains its Draft review status. [Authentication flow](auth-flow.md) owns browser/session sequences; [Google Workspace access](google-workspace-access.md) owns login modes, provider configuration and operating procedures. This document owns the internal authorization, freshness and credential-lifecycle contract.

## Public boundaries and ownership

`src/lib/credentials/index.ts` is server-only. Runtime-free public type modules describe the fixed operations. `src/lib/credentials/internal/` owns session policy, Workspace verification, provider proof, user/technical data transports, provider vaults and refresh. The public client entry `@/lib/credentials/browser` exposes `createBrowserSessionAdapter`; its isolated client implementation cannot import a server credential adapter or Auth SDK.

Shared header caches contain data only. Every invocation authorizes its own actor before a hit or miss and checks its original deadline. A miss uses that invocation's guarded client. The existing keys, tags and 300-second data lifetime are not authorization evidence.

Header projections retain curated Tools, ordered Events and notification recipient/operational-lead filters. Shared people/preference visibility is the existing resource contract, not permission to select another actor or arbitrary private rows.

## Session identity, evidence and live checks

Session transport uses the exact supplied Bearer credential when Authorization is present; malformed supplied Authorization cannot fall back to cookies. Otherwise the private resolver selects the server-owned active cookie generation. Cookie mutations retain approved-Origin checks. Authoritative roles and team identity come from `profiles.auth_user_id = auth.uid()` and `profiles.platform_role`, never editable metadata or client state.

The exact JWT is cryptographically verified. Asymmetric verification uses the SDK's JWKS handling; supported symmetric credentials retain authoritative Auth fallback. Signature validity does not replace current account validity, session admission or profile binding.

Membership evidence is bounded process-local RAM with equal-key single-flight. Its key binds the exact credential fingerprint, user, session, profile, Google subject/email, issuer/audience/scopes, intended action and policy/provider configuration. Expiry is the earlier of the original verification start plus 900 seconds and known JWT expiry. Slow verification consumes that lifetime. Cache hits, copied capabilities, waiting callers and further queries never renew it. Failed acquisition cannot create or extend successful evidence. Separate instances have independent evidence and deadlines; there is no shared evidence store or global RAM invalidation.

Role reads remain live, stricter than ADR 0002's allowed maximum staleness. Auth-user validity, exact profile/Workspace/Google binding, mode, session epoch, current role, known administrator expiry and configuration remain effective at their applicable dispatch boundaries. Scope checks, token usage/accounting, operation claims, ownership and provider expiry are not covered by the membership allowance. An outage cannot renew expired evidence. Established invalid-session, denied and unavailable outcomes remain distinct; cached evidence does not make an action network-free.

Temporary administrator access uses its actual eligible/active snapshot and known expiry. Required snapshot failure denies administration; optional snapshot failure does not remove an otherwise granted planning role. Administrator correction cannot grant CEO decisions, Review governance or personal-token scopes. Development simulation is restricted to the existing local host/environment gate and cannot activate administrator access.

## User data, permits and dispatch preparation

User-context data retains the exact original Supabase JWT, PostgREST JWT validation, grants, RLS and ownership. In Google and enforced-linking modes, each protected database attempt needs its own server-generated permit. The permit binds JWT hash, user, HTTP method, database resource path, access generation and a ten-second lifetime. It never reaches the browser and is not an arbitrary-query forwarding facility.

Writes consume permits atomically. GET/HEAD transactions remain read-only; server cleanup releases their permits after the response. A read permit is not a general one-use guarantee while its request is in flight. Expiry bounds failed cleanup. A permitted read retry needs another live authorization/preparation and permit; mutations are not automatically retried.

Calendar entry uses `workspace_calendar_entry` to obtain Workspace context and mode-dependent session admission in one snapshot. It interprets admission after profile binding, strict identity and OAuth validation to preserve error precedence. Legacy and unenforced linking need no admission permit.

Calendar, `planning.revision.read` and `planning.board.read` use the private `workspace_dispatch_prepare` operation. The compatible `workspace_calendar_prepare` wrapper remains supported. Preparation acquires the configuration ShareLock before validating the captured current context and issuing a session-aware permit where required. These RPCs are service-only, owned by `postgres`, use an empty search path and qualified references. They do not replace the exact user-JWT profile RPC or data request. Other actions retain their existing separate context/permit sequence.

Original JWT and evidence deadlines are checked after live Auth and preparation, immediately before data dispatch. The server generates the permit secret/hash before the writing preparation call, allowing bounded cleanup after a lost or malformed response. Uncertain preparation is never replayed; its private terminal failure prevents an enclosing GET retry from repeating the write. A definite authorization rejection issues no permit. Cleanup failure remains observable without replacing an otherwise successful result or repeating data work.

Service-backed reads retain explicit action, actor, owner and field restrictions; a service key does not substitute for human authorization. Guarded service transports capture effective URL/key/fallback configuration, recheck it after awaited authority checks and before dispatch, and disable generic SDK retries. Confirmed bookkeeping has narrower authority described below. Direct REST/RPC/Storage/Realtime/GraphQL access cannot gain broader rights merely through a valid user JWT. The [Workspace access contract](google-workspace-access.md#authorization-and-data-paths) defines those boundaries.

## Calendar snapshots and private workweek data

`calendar.read` exposes only `readSnapshot(earliestDate)`. The private reader loads published owners and date-filtered publications, follows truncated per-owner history to its relevant tail marker, and validates pagination progress and completeness. Profile pages use exact count and ascending IDs; publication cursors use descending date, revision and ID. Additional pages retain independent live checks, original JWT, permits and cleanup. Errors cannot return a misleading partial snapshot. The multi-request read is not a database transaction; range validation and safe response mapping remain route-owned. Proxy cookie maintenance is independent and shares no route-instance evidence.

Private read/write capabilities remain separate and owner-bound. The read path covers preparing automatic, published, pending and latest non-retired owner data plus one selected edit context. Source/conflict/expired-automatic reads are conditional. User reads retain explicit owner filters and individual permits; the resolving-conflict service lookup additionally binds owner, version and state. Mixed snapshots return `edit_context_stale` with 409. Equal empty edit hashes do not authorize another owner. Saves use only the existing owner-derived draft RPCs. Publication and conflict state machines remain feature-owned.

## Personal Planning Items tokens

The token RPC remains authoritative at authentication and each fixed capability operation. Owner binding, current role, expiry, revocation, scopes, usage accounting and issuance limits remain live. Only Directory membership evidence has the bounded cache allowance. Tokens never inherit interactive administrator activation. Management endpoints bind the session owner; the one-time token issuance response is a deliberate credential-delivery exception, not a general capability result.

Personal actions bind operation, read/preview/commit mode, actor, item and accepted projection IDs. `buildUpdatePreview` prepares one revision from the admitted parsed input and returns its preview plus `validate()`. Validation reauthorizes the operation and executes that same prepared revision in preview mode. Commit uses its own authorized preparation and retains raw-request hashing, idempotency replay, revisions and transaction checks. There is no public caller-supplied revision command or prepared-preview override. [Planning Items API](team-planning-items-api.md) owns wire shapes, scopes, limits and response metadata.

## GitHub credentials and resource authority

Installation JWT signing, key acquisition, issuance and process-local reuse are private. Configuration fingerprints bind app, installation and key; cache entries also bind repository. Reuse ends five minutes before provider expiry. Equivalent misses coalesce, including sanitized failure. Issuance checks captured configuration after the provider response. Each API attempt, existing read retry and asset redirect rechecks configuration and exact token expiry. A usable installation grants no FounderOps role.

`github-http.ts` accepts opaque installation/user resource capabilities. Its private gateway checks HTTPS API origin, allowed repository/search targets, semantic read/write limits, immutable request data and exact supported GraphQL documents/variables. Resource adapters retain domain interpretation, serial mutations and `observe → compare → apply → reconcile`. Provider permission and opaque node/Project visibility checks remain GitHub's responsibility. Installation issuance requests target repository names without inventing broader grants. Asset relay validates its initial target, allowed hosts, each manual redirect, redirect limit and image response; installation Authorization goes only to `github.com`, never the CDN.

GitHub App author OAuth binds a signed ten-minute state to the exact Auth user/profile and safe relative return target. Callback validates the configured login and stores the stable GitHub user ID. AES-256-GCM storage, separate access/refresh expiry and the unique active-account constraint remain effective. Delayed callbacks cannot replace a newer connection. An actual configured-login change invalidates that profile's connection and in-flight refresh.

Vault coordination uses a fresh `connection_id` for each connection, `credential_version` CAS and a durable refresh claim/deadline. Profile-first locking also protects absent-row callback CAS. One owner attempts a rotating refresh across instances; finalization compares configured account, connection, version, claim and original deadline. Expired claims are not reassigned. A lost response may contain an unknown rotated token and requires reconnect, not another exchange of the old refresh token. Omitted refresh material preserves its previous value and independent expiry. Ordinary access retains checked-snapshot use accounting; ordinary status reads do not add token-use marks, while successful rotation retains its accounting.

Authored comment/Review capabilities derive the real author, active task, repository, Issue and live durable claim. They permit only that Issue's reads and marker-bound write. Preview admission is separate. Attachment capability binds current uploader, task permission and exact Contents target. Before dispatch, complete live authority/connection reads, then synchronously check the captured session/claim deadline and acquired provider expiry. A final awaited read cannot extend authority. Installation capabilities cannot upload user-authored attachments.

Attachment operation IDs are retained in memory/session storage after an unknown result and reused only for the same task, filename, MIME type and bytes. Confirmed success clears the ID. Legacy callers use a content-derived target. Every request still authorizes the actor/task. Observe the deterministic target and compare Git blob identity before writing and after uncertain PUT; conflicting content is not overwritten. [GitHub idempotency](github-api-idempotency.md) and [projection architecture](github-sync-architecture.md) own resource recovery and workflow ordering.

## Google Calendar credentials and mutation journals

Calendar connection authority is separate from application Google login and Workspace admission. It binds the current Auth user and mapped owner to the account selected during Calendar consent; the vault does not invent a Google subject/email association. Consent requests `calendar.events.owned`, offline access and the primary calendar. Calendar encryption has its own key. Scope and access/refresh expiry are independent of membership evidence. An owning viewer retains owner workweek access without gaining a planning role.

The constrained transport permits only HTTPS primary Calendar event resources, rejects caller Authorization and follows no redirects. Each attempt rechecks owner/session, connection UUID, revocation, scopes, expiry and captured OAuth configuration. Final synchronous deadline/configuration checks follow asynchronous authority and vault reads. OAuth state and issued-token lifetimes also bound callback probe and persistence. Status retains safe timestamps and bounded primary label probe behavior; unavailable disconnect lookup is a 503.

Calendar refresh uses connection UUID, version CAS, durable owner and original claim deadline across instances. Expired or uncertain refresh is not reassigned. Rotation stores returned refresh material and its expiry atomically; omission preserves the previous values. Delayed acquisition cannot exchange an expired refresh token, and stale provider success/failure cannot overwrite a replacement connection. Ordinary use records `last_used_at` against the checked snapshot. Vault RPCs are service-only.

Reads use `request`; every mutation uses `mutate` bound to the actual owner publication claim/effect or disconnect target. Before HTTP, the transport records dispatch through `dispatch_google_calendar_mutation`, then revalidates live owner/connection authority again. Exact observations also retain durable evidence before confirmation. New publications require write-journal version 1 and a positive immutable generation; published historical weeks stay readable. Deterministic event IDs, owned payloads, generation fencing, ETags, physical reconciliation and write journals remain in the workweek feature. Credential renewal never replays an uncertain mutation.

Disconnect cleanup retains owned-event/ETag/FounderOps-marker evidence and its operation's original connection UUID. A later authorized request can reconcile that cleanup; late local removal cannot delete a newer connection. There is no headless scheduled Calendar recovery; automatic reconciliation is driven by the authenticated workweek controller. Disconnect removes local connection material after cleanup and does not revoke Google's project-wide grant.

## Technical admission, claims and exact completion

| Workflow | Admission and fixed authority |
| --- | --- |
| Notification delivery | POST accepts the configured delivery secret or active administrator; inspection requires active administrator. Digest generation and GitHub reconciliation retain their CEO/deputy session alternative. An invalid supplied technical credential cannot fall back to a session. |
| Outgoing Chat | Fixed space/webhook, configuration checks before use, after issuance and immediately before dispatch. Bot cache binds account/key, audience and scope with original provider deadlines. Failed send never refreshes credentials and replays the message. An explicit 401 invalidates only the matching cached token for a later independently authorized send; late rejection cannot discard its replacement. |
| Webhook intake | Copy bounded raw bytes and captured signature/event/delivery headers before awaits. Verify concrete HMAC on every delivery; headers are not covered by GitHub's HMAC and remain separately bound. New receipt persistence rechecks secret, storage and target configuration. Valid duplicate deliveries reconcile their durable receipt. |
| Scheduled webhook drain | Dedicated Cron Bearer credential, one fixed drain of at most 25 and fixed queue-health reads. Claim selection, retry policy and processing remain domain-owned. Maintenance, delivery, release and human credentials do not substitute. |
| Planning-trash maintenance | Dedicated header secret, strict service credentials and fixed lifecycle/purge operations. Purge remains explicit operator action, limit 25, non-dry-run eligibility RPC and existing parser. |
| Release ingest | Configured machine Bearer credential, captured idempotency key, origin and storage target before body await. Manifest schema/references, canonical SHA-256, exact digest key, 2 MiB limit, immutable-version conflicts, identical replay and atomic notifications remain feature/database-owned. No SDK retry after lost persistence response. |

Notification reservations bind exact claim token, actor, event IDs and original lease. Reserve once; each event permits only its accepted provider attempt, including unknown outcomes. Live preferences, DM target and independent provider capability remain effective. A private asynchronous restriction carries the original delivery/reconciliation trigger into provider dispatch after awaited token acquisition. Concurrent callers cannot borrow that restriction from another request.

Claimed GitHub jobs separately prove immutable family, job ID, lock token and live processing row. Their original lock deadline and the triggering claim-RPC start remain binding. A later read does not renew either. Restrictions compose for the current job; an unrelated expired batch job cannot invalidate valid work. Ordinary installation reads and interactive projection remain distinct from claimed lifecycle work.

Confirmed effects retain only exact existing record/finalize/release authority. They may finish their accepted claim after session, administrator or trigger admission ends, but cannot send again, reserve another event or select arbitrary completion IDs. Captured database URL/key binding remains mandatory, including after secret replacement. Projection lock release and revision finalization require observed successful acquisition/begin results. Workweek bookkeeping binds accepted owner/publication, journal version, generation, acquired operation and exact effect/conflict revision; an already confirmed effect can settle after session loss without granting another provider attempt.

A lost receipt, RPC or external mutation response is not proof that no effect occurred. Preserve durable identity and reconcile on the next independently authorized attempt. Domain-specific replay and finalization remain authoritative; the credential module adds no universal retry or one-time-state protocol. [Webhook intake](github-webhook-intake.md) owns accepted events, human writeback policy, delivery states and recovery. [Google Chat operations](google-chat-rollout.md) owns notification configuration and operating steps.

## Other fixed resources and compatibility

Decision Log is read-only in this application. `decision-log.read` binds the server cookie actor; SSR checks it against the shell actor/role. The private Notion operation queries only the configured data source, with page size 100 and `Datum` descending. Each request has an eight-second limit and the resource has an original 15-second budget beginning at its first query, not initial human acquisition. Subsequent pages do not slide that budget. Feature code owns cursor-loop rejection, mapping, safe links and safe error results. There is no Notion write or new refresh protocol. Retired local Decision Log tables expose no human Data API operation; CEO-only governance remains a separate policy.

Settings writes are limited to the existing focus, profile color/duplicate mode and notification-enable fields; UI preferences and notification catalogs retain their own field sets. Notification preferences use the own-profile or CEO/deputy rule and existing Google Chat conflict key. Governance remains CEO-only. Governance and administrator GitHub Project transactions retain user JWT, permits and database enforcement. Preview storage GET is cookie-authenticated, path-constrained and private/no-store/nosniff, with no signed-URL disclosure. Upload remains contributor-only with current MIME/size limits and generated non-overwriting paths. Release reads retain the 200-release limit, published ordering, active item/PR projection and recipient filter; seen writes bind current recipient/version and `seen_at IS NULL`.

Events retain mapped reads and CEO/deputy or active administrator correction for writes. Tools retain mapped reads and contributor writes; an active Viewer administrator does not gain Tools mutation. Metadata acquisition remains contributor-only and feature-owned, with URL, DNS, redirect and response-size restrictions and live admission at actual fetch after awaited resolution. Notification status changes retain own-recipient or global-event operational-lead authority and existing seen/dismiss transitions. GitHub assets retain contributor admission, exact allowed URL and independent installation authority. Fixed resource operations cannot substitute another method, actor or target.

Ordinary contributor item creation, operations-lead assignment of existing items and scoped personal-token batches are distinct from absent CEO-only interactive intake/AI/bulk-create application actions. Do not invent those actions or a model credential. Legacy Focus endpoints retain their existing owner/role limits without restoring visible Execution UI. Fixed Health inspects only `profiles` and `tasks`; historical Initiative lookup preserves URL compatibility. Login configuration/error pages and the incoming Chat receiver retain public/inert behavior.

The externally dispatched GitHub Actions release publisher is a separate control plane using its repository secret. It is neither an inert receiver nor an application runtime action migrated through the credential module.

## Executable boundaries and verification

`pnpm run verify:credentials` runs architecture fixtures and compiler-resolved dependency checks. The verifier follows imports, re-exports, namespace imports, literal dynamic imports, import-equals and CommonJS across `.ts`, `.tsx`, `.mts`, `.cts`, `.js`, `.jsx`, `.mjs` and `.cjs`, including resolved local helpers outside the initial roots. Type-only imports remain usable. Computed loaders and runtime code generation fail closed; cycles terminate normally.

Only declared resource-protocol edges and bounded transport references are allowed. There is no legacy guard/SDK acquisition exception or directory-wide exemption. Public clients cannot import server entries, private adapters or an Auth SDK. This is deterministic dependency enforcement, not a sandbox for malicious JavaScript. `pnpm run build` checks the source boundary before compilation and scans emitted static client JavaScript/maps afterward. Source and emitted-artifact checks are separate.

Existing focused contracts live in `tests/architecture/`, `tests/unit/auth/`, provider/session suites and the credential integration suites under `tests/integration/`. They exercise invalid/wrong/expired credentials, live authority changes, original deadlines, instance isolation, exact grants/permits, provider uncertainty and finalization. Browser lifecycle cases are in `tests/integration/server-session-browser.test.ts`. These references describe repeatable coverage, not a new run or production acceptance. Local scripted providers do not establish hosted latency or real provider configuration. [Logging](logging.md) defines observation boundaries; [deployment](vercel-deployment.md) defines isolated validation and production procedures.
